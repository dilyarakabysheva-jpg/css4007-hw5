# Учебное руководство по проекту HW5 (на русском)

Это руководство поможет разобраться в коде и объяснить его преподавателю. Читайте его вместе с кодом.

## 1. Главная идея в двух словах

**LangGraph** — библиотека для программы-графа:
- **state (состояние)** — словарь с данными, который передаётся по графу;
- **node (узел)** — обычная Python-функция. Она получает текущее состояние и возвращает **только изменённые поля**;
- **edge (ребро)** — говорит, какой узел выполняется следующим;
- **conditional edge (условное ребро)** — функция, которая смотрит на состояние и возвращает **имя** следующего узла;
- **START / END** — начало и конец графа;
- **compile()** проверяет структуру графа (например, что рёбра ведут к существующим узлам) и делает из него объект, который можно запустить (`invoke`, `stream`);
- **checkpointer** после каждого шага сохраняет состояние в базу (у нас SQLite), отдельно для каждого `thread_id`.

## 2. Порядок чтения кода

1. `helpdesk/data.py` — загрузка JSON-файлов из `data/`. Простой код.
2. `helpdesk/part1_graph.py` — **Часть 1**. Самый важный файл для понимания LangGraph.
3. `helpdesk/tools.py` — **три инструмента** (обычные функции) и `TOOL_SCHEMAS`, то есть описание инструментов для модели.
4. `helpdesk/user_memory.py` — память пользователя (JSON-файл) и поиск фразы «prefer replies in X».
5. `helpdesk/agent_graph.py` — **Части 2–3**: граф с моделью, цикл инструментов, лимит, память.
6. `helpdesk/session.py` — открывает хранилище, выбирает модель, запускает одно сообщение и собирает трассу.
7. `helpdesk/fake_model.py` — **ненастоящая модель** для тестов. Правила написаны вручную.
8. `part1.py`, `chat.py`, `run_scenarios.py`, `reset_memory.py` — команды для терминала.
9. `tests/` — тесты.

## 3. Часть 1 — граф без LLM

```
START → read_request → (choose_next_node) → wifi_help / password_help / other_help → END
```

- `read_request` читает `message` и записывает `category`. Порядок правил: сначала wifi, потом password, иначе other.
- `choose_next_node` — **условное ребро**. Оно ничего не меняет, а только возвращает имя узла: `"wifi_help"` и т.д.
- Узлы помощи берут инструкции из `data/helpdesk.json` и записывают `reply`.

**Сообщение с двумя темами** («My Wi-Fi password does not work.») в исходном графе уходит в `wifi_help`, потому что правило wifi проверяется **первым**.
В изменённом графе (`--variant with_clarification`) `read_request_with_clarification` ставит `category="both"`, и появляется новый узел `clarify_problem`, который задаёт уточняющий вопрос.

**Что контролирует LangGraph:** порядок запуска узлов, слияние обновлений с состоянием, вызов условного ребра, остановку на END.
**Что решают мои функции:** категорию (по ключевым словам) и выбор узла.

Попробуйте сами:
```bash
python part1.py "My Wi-Fi password does not work."
```
```bash
python part1.py "My Wi-Fi password does not work." --variant with_clarification
```

## 4. Часть 2 — модель выбирает инструменты

```
START → load_user_memory → agent ⇄ tools
                              ├→ END              (модель ответила без инструментов)
                              └→ stop_at_limit → END  (слишком много шагов)
```

Как это работает:
1. Узел **agent** вызывает модель. Модель видит системный промпт, историю сообщений и **описание** инструментов (`TOOL_SCHEMAS`).
2. Модель может ответить текстом или вернуть `tool_calls`: «хочу вызвать `check_service_status` с `service="wifi"`».
3. Условное ребро **after_agent**: есть `tool_calls` → узел `tools`, нет → `END`, лимит исчерпан → `stop_at_limit`.
4. Узел **tools** (`run_tools`) — **наш код**. Он вызывает настоящие функции из `tools.py` и добавляет результаты как `ToolMessage`.
5. Потом снова **agent**. Модель видит результат и решает, что делать дальше.

**Ключевая фраза для преподавателя:** модель только **просит** инструмент, а **выполняет** его наша программа (узел `tools`).
Модель не выбирает `status_profile`, `user_id` и `thread_id`. Эти значения берутся из состояния, а туда их кладёт программа из аргументов командной строки.

**Лимит цикла:** `model_calls` обнуляется в `load_user_memory` для каждого нового сообщения пользователя и увеличивается на 1 в `agent`. Если модель хочет инструменты, а `model_calls >= 5`, граф идёт в `stop_at_limit`. Проверка находится в функции `after_agent`. У LangGraph есть свой `recursion_limit`, но в нашей версии он по умолчанию очень большой (10007), поэтому цикл останавливает именно наш лимит.

**Три снимка статуса** (S06/S07/S08) — один и тот же запрос «если работает — сделай тикет»:
- `normal` → operational → тикет создаётся;
- `wifi_outage` → outage → тикет НЕ создаётся, объясняем почему, время ремонта не выдумываем;
- `status_unavailable` → unknown → тикет НЕ создаётся, спрашиваем, нужен ли тикет с пометкой «статус не проверен».

**Защита от лишних тикетов:** в первом реальном прогоне gpt-4o-mini создавала тикеты, о которых пользователь не просил. Поэтому узел `tools` теперь отказывается выполнять `prepare_ticket`, если ни в одном сообщении пользователя нет слова «ticket» (функция `user_asked_for_ticket`). Это правило проверяет код, а не модель.

**Тикет** — это только локальный JSON-файл в `outputs/tickets/`, никуда не отправляется. Поля взяты из `data/ticket_template.json`. Поле `service_status` заполняет **наш код** по последней проверке статуса (или ставит `"not checked"`), а не модель.

## 5. Часть 3 — память

| | Память разговора | Память пользователя |
| --- | --- | --- |
| Что хранит | все сообщения, вызовы инструментов, тикеты одного разговора | предпочтение языка |
| Ключ | `thread_id` (у нас `"user_id:thread_id"`) | `user_id` |
| Где | `local-storage/checkpoints.sqlite` (LangGraph `SqliteSaver`) | `local-storage/user_memory.json` |
| Кто пишет | checkpointer автоматически после каждого узла | узел `load_user_memory`, когда видит «prefer replies in X» |

- **thread_id** — это один разговор. **user_id** — это человек, у которого может быть много разговоров.
- Новый разговор того же пользователя: история пустая, но язык из памяти пользователя доступен (S12).
- Другой пользователь: ни истории, ни языка (S13).
- **Retrieval vs memory:** инструкции по Wi-Fi — это **поиск (retrieval)** в общем справочнике, одинаковом для всех. Язык пользователя — это **память**: личная информация, которую пользователь сам сообщил раньше.
- **Перезапуск:** `run_scenarios.py` запускает каждую часть сценария до и после `restart_process` в **новом процессе Python**. В логе видно, что pid меняется. Память читается с диска.

## 6. Fake model — честно о ней

`helpdesk/fake_model.py` — это **не ИИ**, а набор правил `if "ticket" in text ...`. Он нужен, чтобы:
- тесты и GitHub Actions работали без API-ключа;
- можно было проверить «проводку» графа: инструменты, лимит, память.

Каждый ответ начинается с `[FAKE MODEL]`, а логи лежат отдельно в `outputs/fake_model/`. **Нельзя выдавать эти логи за работу настоящей LLM.** Настоящие логи появятся в `outputs/S06.log … S14.log` после запуска с ключом.

## 8. Вероятные вопросы преподавателя и короткие ответы

1. **Чем узел отличается от условного ребра?** Узел меняет состояние (возвращает обновление). Условное ребро ничего не меняет и только возвращает имя следующего узла.
2. **Следующий узел получает только обновление предыдущего?** Нет, он получает **всё текущее состояние** после слияния обновления.
3. **Почему «Wi-Fi password» уходит в wifi_help?** Правило wifi проверяется первым (`if ... elif ...`).
4. **Кто выполняет инструмент?** Узел `tools`, то есть наш Python-код. Модель только просит.
5. **Как граф понимает, что пора закончить?** Если в последнем сообщении модели нет `tool_calls`, ребро `after_agent` ведёт в END.
6. **Где лимит цикла?** В `after_agent`: `model_calls >= MAX_MODEL_CALLS` → `stop_at_limit`.
7. **Что меняется в состоянии после инструмента?** Добавляются `ToolMessage` в `messages`, обновляются `service_checks`, `reference_ids`, `tickets`.
8. **Чем thread_id отличается от user_id?** thread_id — один разговор, user_id — человек. Предпочтение языка хранится по user_id, история — по thread_id.
9. **Почему память сохраняется после перезапуска?** Оба хранилища — файлы на диске (SQLite и JSON). При старте программа открывает те же файлы.
10. **Почему пользователь B не видит язык пользователя A?** Память пользователя ищется по `user_id`, а ключ checkpointer содержит `user_id`. Модель не может выбрать, чьи данные загрузить.
11. **Зачем fake model?** Тесты в CI без секретного ключа. Она проверяет код, а не качество ИИ.
12. **Почему инструменты — обычные функции?** Их можно вызвать и протестировать напрямую, без модели (`tests/test_tools.py`).
